# Сервис для ведения учëта потребления коммунальных услуг. 

*Цель создания:* Данная система позволяет упростить процесс ведения учëта потребления коммуналтных услуг, исходя из данных в квитанциях.

*Функции:* вход от своего имени, учёт домов по разным адресам, возможность добавления сервиса услуги ЖКХ - вода, газ, свет, мусор и т.д., форма для
  заполнения полей и создания карточки сервиса, ввод показаний данных, суммирование оплаты по всем поставщикам ЖКХ, статус оплачен/не оплачен у каждой
  карточки поставщика, аналитика метрики расхода коммунальных услуг, денег за некоторый период времени(по умолчанию, месяц).

## Стэк технологий

Javascript everywhere, кроме DB.

### Front-end: React.js
Нужно сделать гибридную систему - React.js для веба и React Native для телефонов.
Нужно проектировать компоненты для пользовательского интерфейса с учётом этого.

### Back-end: Node.js
Архитектура: Rest API
Безопасность: JWT
Схема работы: Client --> POST v1/auth/sign-up --JWT response--> Store locally(localStorage for web) --> verify jwt stored locally everytime the request is sent to the server

### DB: PostgresQL
Сущности списком:

- ...

нотация:

Schema даётся вот в таком виде:

Each table has the following form:

table1: id INT PK, field1 TEXT, field2 VARCHAR(100), ... - one-to-many
table2: id INT PK, field1 TEXT, field2 VARCHAR(100), ... - one-to-many
table3: table1.id INT FK, table2.id INT FK - many-to-many

В конце концов, нужно создать Mermaid-диаграмму по этим данным

users: id PK, email varchar(150), password varchar(150) (хранить хешем) - one-to-many
houses: id PK, address VARCHAR(100), hus_paid_status BOOLEAN - one-to-many

users_own_houses: user_id INT FK, house_id INT FK - many-to-many

### Логика работы форм авторизации и регистрации

#### Форма авторизации

*Имеет поля:*
- Email 
- Пароль

*Проверки формы:*
- почта не пуста
- пароль не пуст
- валидация правильности почты по регулярному выражению

*Поведение формы:*
- не пройдена одна из проверок
- неверный логин
- неверный пароль
- успешный вход в систему
- Кнопка "Войти" отправляет форму на сервер по конечной точке "авторзиации".

#### Форма регистрации

*Поля:*
- Имя
- Email
- Пароль

*Проверки формы:*
- имя не пусто
- почта не пуста
- пароль не пуст
- почта соответствует регулярному выражению, валидирующему её
- пароль не менее 6 символов
- пароль имеет хотя бы 1 спец. символ

*Поведение формы:*
- не пройдена одна из проверок
- неверный логин
- неверный пароль
- подача заявки на регистрацию
- Кнопка "Зарегистрироваться" отправляющая форму на сервер по конечной точке "регистрации"

*Notes:*
- Формы авторизации выдаёт токен при успешном ответе от сервера, который в дальнейшем сохраняется локально. Успешный ответ от сервера означает, что вся логика на сервере не дала сбой, и авторзиация прошла успешно.
- Форма регистрации, при успешном ответе от сервера, создаёт заявку на регистрацию вожатого в системе, которую может одобрить только директор.
- Не даём доступ к другими разделам сайта, если пользователь не зарегестрирован валидно. Если нет jwt в локальном хранилище или информация о неподписанном токене пришла с сервера - перенаправляем на форму входа.

### **Требования по разделам разделены по следующему принципу/структуре:**
*Раздел «_Название_раздела_»*

*Внешняя часть (UI)* – словесное описание того, как должен выглядеть раздел графически.

*Логика работы (UX)* – описание того, какая логика должна быть при взаимодействии с клиентской частью – какая кнопка, что делает, что происходит. Логика, когда при каком-то событии нужно отправить запрос на сервер(переход к разделу, нажатие на кнопку), какой запрос отправить, вынесена в раздел Связь клиента с сервером.

*Связь клиента с сервером*
Таблица, показывающая, какой запрос делается и по какому событию на клиенте, напирмер, переходе к основной странице, нажатие на кнопку и т.д. В конечной точке указывается метод и url на сервере, начиная с http://localhost:3000/v1/...
На каждый endpoint, кроме публичных /sign-in и /sign-up, прикрепляется заголовок Authorization: Bearer <token>. По поводу того, какие запросы формировать для сервера и какие ответы получать, см. требования к API со спецификацией Swagger...
Каждое ожидание запроса сопровождается ползунком обновления MaterialUI. Если после выполнения запроса нужно обновить интерфейс до актуальных данных, успешно изменившихся после взаимодействия с самим интерфейсом, то:
1. Весь раздел или часть замораживается, т.е. нельзя нажать ни на одну кнопку, пока запрос в процессе выполнения. 
2. После ответа, UI обновляется до актуальных данных и размораживается. Их также можно дальше изменять с той же самой логикой(заморозки/разморозки интерфейса).
3. Таким образом, если разрабатывается какая-то функция, должно быть указано 2 пункта, обозначающие логику работы интерфейса:
3.1. замораживается после: <после чего именно>
3.2. изменяется: <что именно> 

**Данный раздел описан по структуре:**
*Событие: *
*Конечная точка: *
*Коментарий: *
1.
2.

*Например:*
*Событие: что произошло(нажатие на кнопку, переход в раздел)?*
*Конечная точка: POST users/...*
*Коментарий: тестовый комментарий*
И, если надо, когда логики много и нельзя разрешать пользователю нажимать на все кнопки одновременно:
замораживается после: <после чего именно>
изменяется: <что именно>
